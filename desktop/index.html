Research workflow & authority boundaries
  1. Connect: select the private control credential header; confirm the displayed account and organization.
  2. Create or bring existing work: select or create a project. Record imported observations in a study with imported provenance; file/project migration is not supported by this screen.
  3. Propose: save a research-plan draft, use “Revise this proposal” to declare command, input digest, outputs and limits, then register the experiment design. Coordinator proposals are suggestions, not authority.
  4. Approve: review the immutable plan digest and exact human decision scope. A research-plan approval does not issue an execution grant.
  5. Execute: separately obtain an authorized execution grant through the control API. Select the experiment and variant, choose “Review separate execution admission”, then inspect and explicitly dispatch its admitted attempt. A service worker and configured target are required; this desktop is control-only.
  6. Review and export: inspect operational receipts and quarantined artifacts, review evidence before authoring a conclusion, and export the selected study from the research ledger. Successful execution is not scientific validity.
  7. Reconnect: connect again with a current credential, select the same project and refresh experiment/history. Inspect unknown outcomes before an explicit retry. Closing the window does not stop remote work.

Target, custody and resource policy

Public-released-only data; quarantine-only custody. No runtime installation, raw environment, headers or commands.

Enroll secret — propose metadata first

Never enter a secret on this page or in Connect. Scope is the selected project; provider/audience are bound by purpose. New records start at version 1. A different human principal must propose and the root owner must approve before one-time entry in a hidden native prompt. Salad management and AI Gateway are separate purposes, not interchangeable keys. Live activation remains disabled.

Supported custody: macOS Keychain, explicitly configured native helper and same-host control database. Remote Kubernetes, Windows Credential Manager and Linux Secret Service enrollment are unavailable in this build. Locked/denied Keychain blocks enrollment; no file/env/localStorage fallback. Cancellation consumes the approval: inspect, revoke and purge before a fresh proposal.

Start the local control service
After installing Tessera, run initialization once in a new state directory:
tessera init --state-dir "$HOME/.local/state/tessera-alpha"
Then start the service in a terminal and leave it running:
tessera serve --state-dir "$HOME/.local/state/tessera-alpha" --port 8765
Click Connect, use http://127.0.0.1:8765, then select $HOME/.local/state/tessera-alpha/owner.header in the native file picker. Keep this file private; never paste its contents into chat. On later launches, run only serve. If port 8765 is occupied, choose a free port and use that same port in Connect.
Already have a service? Use its endpoint and private credential header instead. This app does not start a backend automatically or grant execution authority.

    Admit execution attempt
    Operator prerequisite: review retained snapshot contents and release to the enrolled worker, configure project limits, then issue a grant through the human control API for this exact approved task revision, plan digest, snapshot and pinned image. Plan approval is not a grant. See desktop/EXECUTION.md for the supported operator handoff; never paste credentials here.
    Admission binds one existing active grant to this immutable variant before a package can be returned. It does not prepare a package, dispatch, or run work. After admission, the enrolled worker must acquire a lease and prepare a Kubernetes package bound to the returned admitted attempt ID. Refresh the experiment to review dispatch.
    
    
    Authorize Kubernetes dispatch
    Review the operator-supplied exact target digest and worker-prepared package; no ambient Kubernetes context is selected. This creates a target-bound dispatch record only after a package exists. It makes no Kubernetes call and does not prove a run started. The installed worker claims the record and reports its original Job identity, observations and quarantined output. Refresh the experiment and remote workflow to inspect those facts; scientific outcome remains a separate human decision.

    This requests cancellation against the exact displayed recovery and grant revisions. It does not confirm termination, retry the operation, create a new lease, or settle exposure. Record independent attributed evidence through the control API before treating a recovery as closed.
