# Changelog

Tessera remains a developer alpha. Git history records source changes; this page
does not create release tags, a supported binary release or compatibility promises.

## Unreleased

- Large artifacts (ADR 0050): a large output's 4 MiB chunk (about 5.6 MB as base64) could exceed the request size some paths allow (the worker's control channel bounds a request at 1 MiB), and the upload then failed and stalled. Control now takes the operator's `TESSERA_MAX_REQUEST_BYTES` (default 24 MiB, 512 KiB to 256 MiB; also the request body limit it enforces) and advertises `max_request_bytes` and `part_bytes` on large-upload begin and status; the worker sends each chunk in ordered parts of at most the smaller of that and its own channel bound (`part_offset` on the chunk route, one whole-chunk digest, verified when the last part lands), and fails fast with the numbers, instead of retrying, when no part fits or control answers 413. Storage chunks, manifests, custody and composition are unchanged, and a worker or control without parts keeps working as before.
- Snapshot composition: a campaign's `compose_snapshot` step whose sources are chunk-stored (large-artifact custody) no longer fails with "requires a separately issued human_session credential" under an owner-automation-labelled approval. The pre-copy of chunk-stored sources now admits the call's campaign delegation exactly as the command does (read-only check against the recorded approval and intent), so it sees the same delegated actor; an undelegated unlabelled owner, and a delegation its approval and intent do not back, are still refused before any copy.
- Stage scratch (ADR 0059): the operator's scratch and memory limits may now reach 64 GiB (host-checked: memory at most 75% and the ceiling 50% of host memory), and a new operator ceiling `max_scratch_bytes` (poller config, `--max-scratch-bytes`, default 64 MiB) bounds the scratch a stage may request with its spec's `scratch_bytes`. The request is part of the approved plan, granted only within the ceiling and the container's memory, and refused at admission (`scratch_exceeds_operator_ceiling` at submit and approval, using the provider file's `max_scratch_bytes`; the worker's own check at run) instead of failing with `ENOSPC` mid-run. The run receipt and each campaign receipt attempt record the scratch granted. Defaults and existing digests are unchanged. No schema change.
- Large artifacts: completed large artifacts that no manifest lists are reclaimed once their execution is over and they are older than an operator-set age (`TESSERA_ORPHAN_ARTIFACT_SECONDS`, default 7 days; never while the lease is live), by a bounded sweep at large-upload begins (skipped on replays; it examines a bounded window of plausible candidates, so retained, undecided or live-lease artifacts cannot starve newer orphans) and by `POST /projects/{project_id}/large-artifacts/reclaim` for a human (Idempotency-Key required; a known key returns its first answer without sweeping again). The sweep also finishes a rejection whose reclaim never ran. The eligibility re-check and the first delete are one transaction, so a manifest or decision committed after the scan wins. Each reclaim appends one `control.large_artifact_reclaimed` event, claimed by deleting the artifact's upload record, so interleaved sweeps, replays and repeated rejects cannot duplicate it; these events are written outside the command pipeline and carry no command lineage. Nothing is reclaimed while control is held after a restore. Frees chunk bytes in short batches and leaves the quarantine row. Documentation: the operator limit is also checked when a package is built for a stored plan; composed snapshots are not collected; ADR 0050 records the custody and limit changes and amends ADR 0037 and ADR 0040.
- Worker: a stage's observation report that cannot be delivered (for example the confirmed exit of a killed container) is no longer a recorded `unknown` outcome that strands the attempt as `running` until a person cancels it. The runtime's durable `reports` journal is now an outbox with an attempt count and a persisted `next_attempt_at`: the run ends as `report_pending` with no recorded result, and the poller redelivers the same observation (same idempotency key; control already replays repeated keys) after an exponential backoff of 2 to 300 seconds that survives a restart, until control accepts it, permanently refuses it (recorded `observation_refused`) or it is 24 hours old. A confirmed exit supersedes any earlier undelivered non-exit observation, and nothing is invented on control's side: an exit that is never delivered still leaves the attempt `unknown` at grant expiry. See ADR 0054.
- Egress proxy: accept `CONNECT host:port HTTP/1.0` as well as HTTP/1.1. Python <=3.11's `http.client` (and so `urllib`) sends its tunnel request as HTTP/1.0, so every stage using the standard library was refused with 405 and journalled as `method`; the allowlist, cap and target rules are unchanged and other versions are still refused.
- MCP steering (ADR 0055): `tessera_validate_campaign_spec` (a dry-run submit on the control plane: same checks, nothing stored), `tessera_prepare_stage_retry` (offline: a new v2 spec for the stages that did not succeed, pinning succeeded outputs by digest; submits nothing), `tessera_campaign_grants` (read-only grant and release status), and two reduce-only actions for the submitting agent, `tessera_reduce_campaign_budget` and `tessera_revoke_campaign_release` (a finished campaign's release). New routes `POST /projects/{p}/campaign-specs/validate`, `POST /campaigns/{id}/budget-reduction`, `POST /campaigns/{id}/releases/{release}/revoke`, `GET /campaigns/{id}/grants`; no new enrolled action and no schema change. Approval, cap or concurrency increases and grant reconciliation stay human. Gap list: `docs/mcp-steering-gaps.md`.
- Executor enrollment (ADR 0056): `scripts/executor_enrollment.py enroll --existing-project PROJECT_ID` enrolls an executor of any provider into an existing project instead of creating one, so a campaign (one project) can mix a CPU worker and a Salad executor with their data and receipts together. Owner only, an unknown or foreign project is refused before anything is issued, the request is journaled, and repeating the identical command in the same directory is a no-op; `executor.json` gains `project_existing`. Trust is unchanged: the principal still has to be listed under its provider. No schema change.
- Inputs: the worker's chunked-input verifier, the Salad workload contract's `input.max_bytes` ceiling, the guardian input path and the GPU runtime's mirrored constant now follow the operator artifact bound (`TESSERA_MAX_ARTIFACT_BYTES`, default 8 GiB) instead of a fixed 2 GiB, so a multi-GB custody artifact can be a Docker or Salad stage input. The GPU workload image must be rebuilt and re-pinned. Salad stage outputs stay at 16 MiB. Tests drive the guardian client against a fake control serving a virtual 3 GiB artifact.
- Large artifacts: a stage output above 16 MiB (for example model weights) is now moved and held with bounded memory under one sha256 over the whole file: the worker streams it in 4 MiB chunks through new `large-artifact-uploads` routes (same lease, grant, epoch and path fences; resumable; per-chunk and whole-file verification at completion), control quarantines it as an ordinary artifact whose bytes are chunk rows, manifests list it, and custody release plus composition copy it chunk by chunk into a chunked snapshot that local Docker, self-hosted and Salad stages consume as an input. Operator limits: `TESSERA_MAX_ARTIFACT_BYTES` (default 8 GiB, was an implicit 16 MiB output bound and 2 GiB chunked-snapshot bound), `TESSERA_MAX_PROJECT_ARTIFACT_BYTES` (default 32 GiB, was 8 GiB), the worker's `max_output_bytes` and the adapter's `max_input_bytes`. Outputs of 16 MiB or less, and Salad stage outputs, are unchanged. See `docs/large-artifacts.md`.
- Campaigns: an egress policy may carry optional `sources` (license and source per allowlisted host, part of the approved plan and recorded as a declaration, never verified), and each campaign receipt attempt with egress now records the approved egress policy and the worker's egress journal (sha256 and summary). Stages without egress, and egress policies without `sources`, keep their digests and receipt shape. `tests/test_campaign_public_fetch_stage.py` proves a public-input fetch stage feeding a no-egress stage (outputs above 16 MiB later moved to large-artifact custody, below).
- Campaigns (ADR 0048): submit and approval refuse a stage whose grant lifetime is shorter than `max_duration_seconds` plus a 300 s margin (`grant_shorter_than_stage_duration`); the CPU `grant_ttl_seconds` bound rises to 43200. The runner issues a grant, and starts its lifetime, only when the project limits and a worker slot are free (`worker_slots`, 1-8, default 1, per `local_docker`/`self_hosted` entry; a grant whose launch the worker reported refused frees its slot at once, ADR 0046) (`campaign.stage_waiting_slot`), restarting the anchor at issue so waiting never shortens it. Expired grants whose operation has a confirmed exit and a recorded cost are reconciled automatically on the runner tick (`execution.expired_terminal_grant_reconciled`), never without that evidence and never from under an in-flight or unknown campaign attempt. No schema change.
- Campaigns (ADR 0053): the runner resolves an `admitted`, `running` or `unknown` attempt whose worker confirmed the exit with no contradicting observation. The grant and its slot are released and the cost recorded (never above the hold) in one transaction, the attempt becomes `failed_transient` / `exit_confirmed_unresolved` (or the declared or undeclared exit-code class from a run receipt), the stage returns to its normal retry path, and the receipt shows `exit_resolved` as no evidence. An attempt with no such evidence stays `unknown`; billable and route-based (Salad) providers are untouched, and a live lease or an upload in progress is never overtaken; no schema change.
- Worker: optional operator-owned `docker_network_pool` (private IPv4 CIDR) and `docker_network_prefix_length` (default 24) for the Docker networks Tessera creates, for hosts where Docker's default address pools are exhausted. Each run's egress network gets an explicit free `--subnet`/`--gateway` (skipping existing Docker networks and host routes; the daemon arbitrates races), is labelled `tessera.operation`, removed at run end, and the poller prunes only unattached Tessera-labelled orphans at startup. Unset keeps Docker's default pools. A failed network create is now recorded as `launch_failed_network_create` with Docker's error (nothing was created or started) instead of an unconfirmed prepare.
- Provider trust (ADR 0047): optional owner-set `mode: all_registered_providers` gives every principal listed under a registered provider every data class, so agents and specs route data among configured providers without a per-run approval; unlisted principals and unregistered provider ids stay public-only, specs and approval-time settings still narrow, and the egress refusals for non-public inputs are unchanged in every mode. The default mode is omitted from the canonical form, so existing setting digests do not change.
- Worker (ADR 0046): the development CPU worker reports a definite launch refusal (egress network or container create refused, no container) as the closed `launch_error` class on its unknown observation; its report journal gains a `launch_error` column in place. Lost replies and timeouts are never reported as launch errors.
- Campaigns (ADR 0046): the runner reconciles an unknown attempt whose worker reported a refused launch (closed `launch_error` class; zero hold, expired zero-exposure grant, no container id, provider resource, receipt or manifest) as `not_started` with zero settlement, re-queues the stage without using a scientific retry, and records it on the timeline, frame settlement and receipt as no evidence. Identical repeats stop at two per stage and block with the reason. A host reboot or an unreported start is not a trigger and, like any attempt that held money or shows container evidence, keeps the human path. Worker observation reports accept an optional closed `launch_error`; no schema change.
- Recovery: `tessera backup` and `tessera restore` take an operator size bound `--max-backup-bytes` (default 1 GiB, at most 64 GiB). Every recovery deadline, including the SQLite validation handler, scales with it (30 s per started GiB), and a size refusal names the setting.
- Worker: heartbeat idempotency keys are unique per heartbeat journal (a random journal id kept in the journal file), not derived from the sequence alone. The grant poller gives each grant a fresh workspace, so the old keys repeated across grants under one worker credential; control answered them as replays, the worker's liveness was never refreshed and later leases were refused as disconnected. A pending key is still replayed after a restart.
- Worker: the development worker renews a running operation's 30 s control lease on its first pass (including after recovery), then every 10 s of elapsed time as well as every 15 ticks, and never sleeps past the next renewal. Counting ticks alone let a `poll_seconds: 2` poller (the documented example) lose the lease after about 30 s, so control refused the next package refresh and the worker killed every CPU run longer than that.
- Worker: on native Linux the 0700 output workspace is owned by the poller's uid but CPU stage containers ran as 65532, so no stage could write its declared outputs. The development poller now takes an optional operator-owned `container_user` (numeric `uid:gid`; config file, `--container-user`, development worker config) passed as `--user`; plans and specs cannot set it. The default is the poller's own uid:gid on native Linux (root poller and other platforms keep 65532:65532), uid/gid 0 needs `allow_root_container_user`, the workspace stays 0700 with all custody checks unchanged, and the effective user is bound into the durable fence digest (the journal stores the digest, not the user), so a restart with a different user refuses the recorded operation. Images must keep their files world-readable or owned by the configured user (see `docs/campaign-providers.md`). **Upgrade note:** the digest now covers the user on every platform, so drain CPU operations (let running and uncertain ones finish or be cancelled) before upgrading; an operation journaled by an earlier build fails its digest check afterwards rather than resuming. Rootless Docker, `userns-remap` and a poller with uid or gid 0 need an explicit `container_user` (see the docs).
- Worker: the development poller takes optional operator-owned `memory_bytes` and `scratch_bytes` (config file, CLI and worker config; 32 MiB-1 GiB and 1-64 MiB) applied to every container it runs; unset keeps 256 MiB and 16 MiB. `scripts/executor_enrollment.py enroll` also accepts `--provider local-docker` and `--provider self-hosted`, giving a CPU poller one stable, renewable principal to list in the provider trust file.
- Campaign gates (ADR 0045, schema v69): conditional inter-campaign unlock (human gate go or platform-computed paired-delta outcome, evaluated in the admission transaction and recorded on the receipt), paired-delta replicate groups, human-only gate decisions, and an operator program budget (`--program-budget`) that only narrows existing caps.
- Operators: `tessera-garage-operator` now names its gateway `control-gateway` by default (set `TESSERA_GARAGE_GATEWAY` to keep an existing host's TLS name and origin). `tessera-k8s-operator` and the route supervisor refuse to start unless `TESSERA_REPOSITORY` names the fixed target (the working directory is no longer used), and a colon-separated `KUBECONFIG` uses its first entry. The Salad operator validates `--organization`.
- Salad guardian: a request alarm or provider deadline (`TimeoutError`) is reported as the closed refusal code `service_deadline` instead of `internal` (the driver still treats it as terminal), and for `internal`/`service_deadline` refusals the guardian journals the exception class name only.
- Salad create: a create POST that provably never left the process (a DNS or connect failure before any request bytes, the credential guard, or a local error before the request) is reported as `request_not_sent` (summary status 0) and released through the create-rejected path on the guardian's own absence reads after the settle bound, instead of holding the single-operation fence until the route deadline plus the lost-create margin. The live-check receipt reason is `create_not_sent`; a failure after the POST was sent stays uncertain.
- Code approval (ADR 0039 follow-ups): a file approved as code in any snapshot cannot be declared public data in another snapshot; a snapshot's own malformed manifest or approval refuses only that snapshot, and another snapshot's corrupt row no longer blocks staging org-wide; `_approved_elsewhere` reads only approvals that list the digests; a release of a snapshot with approved code reports `contains_approved_code` (response and event); ADR 0039 text updated. The v62 migration tests now build a real v62 database from `tests/fixtures/state_v62.sql` (regenerate with `dev/make_v62_state_fixture.py`).
- Salad guardian: the rate read and the group/instance reads each get their own 4.5 s retry window per loop pass (a slow rate read no longer starves a group-read retry); the worst-case loop-pass allowance is 12 s, inside the 45 s unseen-run gap.
- Salad guardian: the loop-pass allowance is now computed from the worst case (4.5 s retry window + two first-attempt reads + 1 s = 9.5 s) and `UNSEEN_RUN_GAP_SECONDS` rises from 40 to 45 s to keep its bound (slightly more conservative accrual backdating). Read-failure fields are documented as most-recent-ever with `*_at` timestamps, and failed diagnostic writes are counted (`diagnostic_write_failures`).
- Salad guardian: the shared provider-read retry window is 4.5 s (inside the 5 s loop pass) so a read that failed by timing out still gets one retry; a read that gives up records its closed reason (`last_rate_read_failure`, `last_provider_read_failure`; receipt `guardian_last_*_read_failure`), and stale or invalid rate observations now report `rate_stale` / `rate_observation_invalid` internally (the caller still sees `rate_unknown`).
- Salad guardian: a refused workload call records its closed refusal code (deduplicated per minute) as `last_workload_refusal` in status and `guardian_last_workload_refusal` on the live receipt. The stop-cause lookup no longer treats `_` as a wildcard, and the docs state exactly what the shared provider-read retry window bounds.
- Salad guardian: group/instance reads get the same bounded, fail-closed retry as the rate read (transient failures only, cumulative `provider_read_retries`); all provider-read retries in one loop pass share one 4 s window. The guardian records the first cause of its own stop decision (`stop_cause` in status, `guardian_stop_cause` on the live receipt).
- Salad live check: a read-only `observe` whose fresh provider read timed out (`ProviderReadUnavailable`, still a 409) is skipped and retried at the next interval, at most twice in a row (`observe_transient_failures` on the receipt); a third consecutive failure or any other error still ends the run with the exact stop. The guardian keeps its own heartbeat and stop authority meanwhile.
- Packaging: `deploy/executor/` ships an example systemd service and timer that renew a stable executor enrollment twice a day (installed under `share/tessera/deploy/executor`).
- Salad guardian: a failed published-rate read is retried at most twice within the loop pass (short backoff, 4 s budget, every attempt still exact and at most 5 s old); when all attempts fail the rate is unknown and the run fences and stops as before. Retries are reported as `rate_read_retries` (status) and `guardian_rate_read_retries` (live receipt).
- Stable executor enrollment: `scripts/executor_enrollment.py` (`enroll`, `renew`, `revoke`, `show`; module `tessera_control.executor_enrollment`) keeps one owner-enrolled worker principal per provider instance in a private directory, so the ADR 0040 provider trust file can list it once. `salad_live_setup.py --executor-dir DIR` reuses its project, principal and registration instead of minting them per route; in the shared project each route raises the execution limit by exactly its own cap and admits one more grant than are unresolved (at most 7 before rotation). Control now refuses any worker-credential renewal past seven days after issue; route setups also check the bound against control's credential row. The token is never printed. See `docs/provider-trust.md` (Stable executor).
- Salad guardian: an operation whose allocation became uncertain is closed automatically (`reconciled`, reason `provider_confirmed_exact_group_stopped`) once a fresh exact provider read shows the group stopped with zero instances: stop retries end, accrual freezes and the orphan fence releases; custody stays unsealed and outputs unimportable. The live driver reports `provider_stop_confirmed` separately from `stop_confirmed` and stops waiting.

- Salad cleanup: `tessera_control.salad_group_cleanup` plans, and against a non-live provider port applies, audited deletion of stopped, zero-instance container groups, driven only by the calling worker's own route records (never lists the provider; bound id and exact `attempt-<operation id>` name required; read-back, then a durable `begin` bound to the evaluated route revision, then a second read before the one-shot delete, aborting on drift; an unconfirmed delete leaves the route `unknown`, never `stopped`; intent and outcome audit events `remote.group_cleanup_recorded`; synthetic receipt marked as a non-live read-back, no cost relief). `tessera-salad-cleanup` is a dry-run-only operator CLI over a read-only state directory. `TrustedSaladServer.cleanup_settled` is an off-by-default hook that refuses unless both the server transport and the explicit port are marked non-live, so against a real server it always refuses; there is no production port. A sent delete whose receipt or outcome audit is refused is reported `delete_unrecorded`, and cleanup audit events are validated strictly. Live group deletion has no activation gate, so live activation stays blocked.
- Test tooling: `dev/focused_tests.py` runs the tests of the changed modules and their direct dependents with `-x` (a test named for or importing a changed module, plus the tests of source modules that import it; docs or harness changes select the docs-link or harness tests); an empty selection runs nothing. The Makefile provides `make test TESTS=...` and `make test-parallel` (concurrent disjoint shards, no xdist) for the once-per-branch pre-merge run.
- Packaging: the worker deployment examples under `deploy/worker/` ship in the installed layout.

- Worker daemon: `tessera-worker-daemon run -- <subcommand> ...` supervises a worker command (`development-run`, `development-poll`) with exponential backoff, a long backoff after a rejected credential, graceful SIGTERM handling, a single-instance lock and a `status.json` health file; `deploy/worker/` has systemd and launchd examples with placeholder paths and `docs/worker-deployment.md` is the operator guide.
- Worker CLI: exit status 3 means control rejected the worker credential (one bounded stderr line, `credential_rejected` in the JSON result); 2 stays terminal evidence. A 403 whose control `detail` is exactly one of two known authority-gone strings (worker not assigned to the grant, worker retired) is a permanent refusal; any other 403 is treated like a credential rejection. A restart with a broken refusal journal cannot start the provider again (tested).
- Platform validation harness: a failed post-run resource listing makes the residue case GAP; database helpers close their connections; a control outage whose worker never returns is a FAIL; the recovery case no longer implies recovery succeeded and a separate `provider-effect-reconcile-after-crash` case reports GAP until recovery reaches a confirmed exit with a verified receipt; the direct-connect classifier and residue logic have offline tests.

- Development worker: a 401/403 on the run-receipt post is not recorded as a terminal refusal (fix the credential and restart to repost); a failure to write or read the durable refusal journal is a terminal `run_receipt_refusal_unrecorded` outcome; the journal's connections are closed deterministically; the operator reset for a recorded refusal is documented in `docs/cpu-runtime.md`.

- Local Docker fixture: `stop()` treats a failed `unpause`/`kill` as benign only when a fresh inspection shows the container is no longer running (an exit race); a vanished or still-running container stays unknown. The pre-termination calls keep the 2 s bound.

- Local Docker fixture: cleanup absence is an exact-ID `container ls --filter id=` query (no full host listing) and post-termination cleanup calls have a separate 10 s bound; all other Docker calls keep 2 s and timeouts still fail closed to `unknown`.
- Run receipts: control now verifies each docker-local-cpu run receipt against its own records (operation id, plan digest, argv-derived command digest, and its artifact manifest digest/tenant/lease/epoch binding) and refuses mismatches or missing records with a fixed 409; the worker cites control's manifest digest as `output_digest` and keeps its local seal digest as `receipt_payload.sealed_manifest_digest`.
- Development worker: after a confirmed exit and sealed output the docker-local-cpu worker posts one observed run receipt (facts only, deterministic idempotency key); a refused or failed post reports `unknown`/`run_receipt_failed` and keeps custody.
- Development worker: run-receipt posts retry transient control failures (3 attempts, one key); a permanent HTTP 4xx refusal is recorded durably, reported as terminal `unknown`/`run_receipt_refused`, never replayed on restart, and makes the CLI exit 2.
- Local Docker fixture: `--cases` selects an exact subset of cases (partial states only);
  weak-class runs on Docker Desktop reached live cancel, deadline and broker-loss with
  confirmed termination and cleanup (ADR 0035).

- Local Docker fixture: explicit, operator-selected weaker attestation class
  `engine_declared_workload_observed` ([ADR 0035](docs/decisions/0035-docker-desktop-network-attestation.md));
  the strong `daemon_host_independent` default and its plan digests are unchanged.
- Local Docker fixture weak class: accept the kernel's reviewed fallback tunnel devices only when
  DOWN, unaddressed and unrouted, with a bounded path-free network diagnostic; the strong class is
  unchanged ([ADR 0035](docs/decisions/0035-docker-desktop-network-attestation.md)).
- Local control and desktop research records, separate approval/admission and
  worker execution, artifact quarantine/custody and governed agent interfaces.
- Explicit schema migrations and SQLite/project-object backups; restored history
  remains permanently held and does not fence original services or external jobs.
